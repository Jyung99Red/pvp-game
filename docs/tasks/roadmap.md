对战这一轮用户要在手机上试（两台设备，一台建房一台加入，两边都看）：
- 走路时黑色阴影的边还跳不跳；**加入的那一台**走路和出招还卡不卡（原来主要卡在加入的一方）。
- 贴着东西两侧的墙、内墙的侧面站，墙应该完整；站到南墙或内墙北侧被挡住腿时才透。
- 一台切到后台几秒再回来：另一台显示"对方暂时离开，等待中…"，回来后倒计时 3 秒接着打。切出去超过一分钟会中断。
- 格挡 120°：侧面偏多少开始挡不住，打怪时（怪绕到侧面、狼的扑击）会不会太容易漏；对战里绕背好不好用。
- 视野 150°（冒险里也有）：身后一大片是暗的，习不习惯；怪物或对手绕到身后突然消失、转身又出现，会不会太突兀；
  身后的怪出招时没有红区，挨打前来不来得及转身；要不要给身边留一小圈看得见的范围；据点里要不要关掉。

怪物看墙和绕路用户要在手机上试（现在的地图墙少，千柱窟和首领房最容易看出来）：
- 隔着 2 格以上的墙走近怪，它应该没反应；绕到看得见的地方才出"!"。
- 被追着的时候绕到柱子或墙后面：怪应该绕过来，不再顶着墙原地走；绕路时脸朝走的方向。
- 走开脱战后，怪回家也会绕墙。
- 会不会太难甩掉、或者绕路的路线看着别扭。
- 身边一小圈：怪贴在身后时看不看得见它和它的红区；1.5 格够不够、会不会太大；对战里对手绕背还有没有用。
- 狼和狼王的撕咬：红区往前短了一点（野狼约 0.12 格，狼王约 0.15 格），感觉够不够；野狼从最远处咬过来时及时后退能躲开，会不会又变成"退一步就躲开"。
- 水潭现在的地图里还没有，重画地图时才会出现。

画质第一步用户要在手机上试：
- 整体颜色：据点偏暖、山谷偏冷，会不会太过；亮的石板地还刺不刺眼；背阴的墙面是不是太黑太蓝。
- 墙根和内角的暗边自然不自然。
- 洞穴里点火把：墙后面应该是黑的，光的边是柔的；穿透墙看到的地面应该是碎石。
- 帧率和以前比有没有掉（开着帧率显示在各个地区走一圈）。

M12 用户要在手机上试：
- 挡得住吗：连段打完还来不来得及挡下一下；看到红区再按格挡来不来得及，特别是狼王快咬（0.65 秒，狂暴 0.52）和野狼撕咬（0.72 秒）；拿火把用剑挡。
- 弹反：快招看到就按多半是弹反，慢招（头目震地 1.5 秒、猛扑和扑击 1.15～1.35 秒）要等，这样的分别好不好；敲铁声沉不沉；白闪 0.2 秒看不看得清。
- 撕咬的摆头看不看得出从哪边来、红区扇形清不清楚、侧走确实躲不开。
- 节奏：同一只怪的快招和慢招有没有快慢变化；轻招后的空档（打两三下）和重招后的空档（打一整套）够不够。
- 新动作：斜斩、回扫、重斩有没有力量感；蓄力斩的低扫；跑步 1.5 秒开始合不合适。

## 3. 新会话怎么开头

直接发：

> 看 `docs/tasks/roadmap.md` 和 `docs/tasks/design.md`，做 <要做的事>（比如：第 2 节第 2 条，交互动作）。数值在 `game_config.js`，对照表是 `docs/tasks/parameters.md`。
> 遇到没写到的问题按最简单的做法做，并记进 `design.md`。做完测试全绿、提交推送，然后告诉我要在手机上试什么。

约定（也在 `AGENTS.md`）：

- 改动直接提交并推送到 `main`，不另开分支（用户 2026-10-02）。
- 可调数值只放 `game_config.js`，改了同步 `parameters.md`。模型形状和关键姿势是 `models/` 里的数据，不是可调数值。
- 新脚本登记到 `client-assets.json`；新页面片段还要在 `index.html` 里加 `#mount-<id>`（动作调试页的在 `tune.html`）。
- 完成 = `node --test "tests/*.test.cjs"` 全绿。改了测试断言的内容要说明为什么。
- 代码注释和 `AGENTS.md` 用英文；`README.md`、界面文字、`docs/tasks/` 用中文。
- 文档只有 3 份（这份、`design.md`、`parameters.md`）。新决定写进 `design.md` 对应的节，不另开文件，不写"某某里程碑补的决定"这种流水账。

## 4. 自己能测什么

云端容器里预装了 Chromium 和 Playwright（全局在 `/opt/node22/lib/node_modules/playwright`），无头模式下 WebGL 用软件渲染能跑、能截图、能模拟横屏手机和两根手指。

| 能自己测 | 怎么测 |
|---|---|
| 模拟规则：连段、派生、预输入、停顿线、格挡条、卡肉、失衡、药水 | Node 测试，直接驱动模拟 |
| 判定：每招必中、扫过的角度、矮的怪能被打到、红区 | Node 测试 |
| 联机协议和同步 | Node 测试里主机和访客各跑一份（`tests/duel.test.cjs`），可以加延迟、加抖动（每条消息延迟不同）、让一方"切到后台" |
| 页面加载、没有控制台报错、资源清单完整 | 浏览器测试 |
| 画面、按钮布局、文字有没有被挤掉 | 截图后用 Read 打开看 |
| 两根拇指同时操作 | CDP 多点触控 |

| 测不了，要用户在手机上试 | 原因 |
|---|---|
| 手感：按钮位置、连段节奏、走路快慢 | 要真手指 |
| 真实帧率 | 软件渲染只有几帧每秒；能比较的只有绘制次数和三角形数 |
| iPhone 的方向锁定、全屏、安全区 | 容器里只有 Chromium |
| 音效 | 听不到 |
| 两台设备真实联机 | 连不上公共信令服务器 |

### 4.1 浏览器测试的写法

- 启动：`chromium.launch({ args: ['--use-gl=angle', '--use-angle=swiftshader', '--enable-unsafe-swiftshader'] })`。
- 横屏手机：`browser.newContext({ viewport: { width: 844, height: 390 }, hasTouch: true, isMobile: true, deviceScaleFactor: 2 })`。
- 多点触控要开 CDP 会话用 `Input.dispatchTouchEvent`（`page.touchscreen.tap` 只能单点）。
- **不要依赖真实时间**：无头模式两帧之间有时隔 0.5～0.75 秒。用 `game.pause()` 停掉实时时钟、`game.run(秒)` 确定地推进；真要测实时循环就等"已经跑过几帧"。
- `tests/browser-smoke.test.cjs` 就是这套办法，找不到 Playwright 时自动跳过。设 `SMOKE_SHOTS=<目录>` 会存截图。
- 用户的 Windows 电脑上：把 `playwright-core` 装在任意目录，设 `PLAYWRIGHT_MODULE=<该目录>/node_modules/playwright-core` 和 `PLAYWRIGHT_CHANNEL=chrome`。

### 4.2 页面上的 `window.game`

- `game.pause()`、`game.run(秒)`、`game.sim`（模拟状态）、`game.map`（当前图）、`game.panel`（打开的面板）、`game.screens`（背包等界面）。
- `game.load('base' | 'field' | 'valley' | 'cave' | 'clearing')` 换区域（从头进），`game.save` 是存档，`game.persist()` 立刻写存档。
  每个浏览器测试用新的 `BrowserContext`，存档从头开始。地址里 `?map=` 直接进某个区域。
- `game.duel` 是对战会话，`game.room` 是房间界面；对战页面不要 `game.pause()`（对局靠真实时间）。
- `game.view.ground.cut.on.value = 0` 关掉镜头遮挡透明；`cut.open.value` 是当前开合程度（0～1，被挡住时渐开）。
- 看模型近景：先 `game.view.render(game.sim, 0)`，再把 `game.view.render` 换成空函数，自己摆 `game.view.camera` 并 `game.view.renderer.render(game.view.scene, game.view.camera)`。
- **调姿势**：现在用动作调试页（第 4.5 节）。控制台的老办法也还能用：在浏览器控制台 `game.pause(); game.sim.player.act = { move: 'smite', phase: 'swing', t: 0, from: null }` 定格在某招的起手
  （`t` 换成 `gameConfig.combo.moves.<招>.swing` 是挥完），再改 `playerMoves.moves.<招>.a.<骨>.rx = …`，画面马上变；
  `game.sim.player.facing` 转人物（1.57 正对镜头）。只在这一页有效，调好的数写回 `models/player_moves.js`。
- 怪物测试用固定的场地 `tests/fixtures/m3-field.cjs`（游戏里的区域会跟着内容改，测试场地不变）。

### 4.5 动作调试页 `tune.html`

- 和游戏同一个启动器，清单里是 `tune` 这一项（只有核心、模型和 `tune/`，不带游戏界面）。`tune/lab.js` 是工作台（不碰页面和 three.js，Node 测试直接跑）：
  改关键姿势（写时复制，几个招共用的盾臂不会被带动）、单招和其他姿势的预览、连段用真的模拟按招式表出（每一下在派生点刚好接上，停顿招在过了停顿线后按）、
  和 `tests/hits.test.cjs` 一样的量法（从站姿、不算踏步）、把改动写成源码。`tune/view.js` 只画，`tune/panel.js` 是页面。
- 身体每一帧都自动落地（`core/player_anim.js` 的 `grounded`：最低的方块贴地），所以 `base`、`pelvis` 的 `py` 没有效果，蹲低只能靠弯腿。
  现有招式里的 `pelvis: { py: … }` 因此都不起作用（2026-10-04 查到，没改）。
- 骨头的三个数是欧拉角，旋转是 `Ry · Rx · Rz`（`core/math3d.js`），所以滑块绕的是万向节的轴，不是骨头自己的 x / y / z：
  ry 绕上一节骨头的 y，rx 绕被 ry 转过的 x，rz 绕这根骨头自己的 z；rx 到 ±1.57 时 ry 和 rz 的轴重合，少一个方向。
  手腕大多数招式都在这附近（剑和小臂快成一条线），单拖滑块摆不出想要的角度（用户 2026-10-04："rx ry 不是跟着三维线转"、"怎么都调不到"、
  "单独手腕也应该能摆成任意角度"）。这不是引擎的限制，是姿势的存法；游戏核心没动，改的是工具：
  - 画面上选中骨头的三根线是它自己的轴（`lab.frame`，永远互相垂直）；每根骨头有"绕自身轴"X / Y / Z，按住左右拖就绕这三根线转
    （`lab.turn`：从拖动开始时的姿势转整个角度，再算回三个数，取离原来的数最近的那一组，所以数字不会乱跳）。
  - 鼠标放到滑块上（或焦点在滑块上）时多画一根虚线，是这个滑块实际绕的轴（`lab.gimbal`）。
  - 两个关键姿势之间仍然是三个数各自线性过渡，所以绕自身轴摆出来的姿势，中间过程要在预览里看一眼。
  每个改过的数（姿势和节奏）旁边有"原 … ↺"按钮，只还原这一个数（用户 2026-10-04）。
- 节奏能实时改，是因为 `tune.html` 在加载前设了 `window.unfrozenConfig = true`，`game_config.js` 在这一页不冻结；游戏和测试里照常冻结。
- 草稿存在 `localStorage`（`blockKnight.tune.draft`），只记和文件不同的地方，每一项连同调的时候文件里的值（`base`）一起记。
  页面每次打开都读最新的文件，再逐项对草稿：和文件一样的（已经写回了）清掉；文件在那之后又改过的，以文件为准，页面上提示是哪几项，用户可以选"还是套用我上次的草稿"；其余照常套用。页面上 `window.tune` 给测试和控制台用（`tune.lab`、`tune.rec`、`tune.time`、`tune.pause()`）。
- **用户贴回导出的代码时**：招式那段整段替换 `models/player_moves.js` 里同名的招，节奏那行替换 `game_config.js` 里同名的行（改了节奏还要同步 `parameters.md`），
  其他姿势按注释里的位置放。然后跑测试：用户有意改了一招的形状时，`tests/hits.test.cjs` 里这招设计的扫角、起止方向可能要跟着改，改了要说明是用户定的。
- 测试：`tests/tune.test.cjs`（导出的代码和文件一字不差、改动不串、草稿遇到改过的文件、体检和判定测试一致、连段时机），`tests/browser-smoke.test.cjs` 最后一个（页面能用、草稿刷新后还在）。

### 4.6 地图预览页 `map.html`

- 只读，不是编辑器（用户 2026-10-04：编辑器可能太复杂；先能看着坐标说哪里要改）。清单里是 `map` 这一项（`game_config.js`、`core/terrain.js`、`core/props.js` 和 `mapview/`，不带 three.js）。
  `mapview/plan.js` 把一张地图变成画图和描述用的数据（不碰页面，Node 测试直接跑），走游戏同一个加载函数，所以看到的就是游戏加载的；`mapview/page.js` 是页面和 2D 画布。
- 用法：选地图（或地址加 `?map=field`）；上边和左边是列号、行号（列从西边 0 往东，行从北边 0 往南）；指到哪格显示 `field (23, 5) 野狼 w`，
  点一下得到 `field (23, 5)`，拖一个框得到 `field (20,10)-(30,15)`，自动复制，也在右上角的框里。
- 可开关的显示：怪物的警戒圈和追击圈（拴绳）、传送门去哪和过来站哪、建筑宝箱出生点木桩、一屏范围（手机横屏看得到的地面，按相机算，北边远南边近）、量距离（直线和走路各多少格、走和跑各几秒）。
- **总览**（地图下拉框第一项，或 `?map=world`；用户 2026-10-04）：游戏里各区域是各自独立的地图，没有全局坐标，这里把它们摆到一张纸上看全貌。
  从据点开始，门从哪边出去，那张图就摆在哪边，回来的门和出去的门对齐，摆不下就顺着那个方向往外挪；没有门通到的（竞技场）排在最下面。
  连线是一对传送门，虚线是要先打倒首领的，粉色是"两头方向对不上"（比如从据点往东出去，到山谷却是从南门进）——重画地图时照着改。
  指到哪块区域，显示的是那张地图自己的坐标；点一下打开那张图。算法在 `mapview/plan.js` 的 `world`。
- 挡视线的方块（2 格以上的墙、树、建筑、枯木丛）和矮障碍（1 格的石头、矿）画法不同。游戏会拒绝的地图照样画出来，错误用红字写在旁边。
- 改地图的流程：用户说坐标和要改成什么，改 `game_config.js` 里的字符行，刷新预览页看，测试会检查走得通、传送门落脚点安全。
- 页面自己的颜色、格子大小、手机屏幕比例（844×390）是页面的数据，放在 `mapview/` 里，不在 `game_config.js`。
- 测试：`tests/mapview.test.cjs`；`tests/browser-smoke.test.cjs` 最后有一条（没装 Playwright 时跳过，这一条还没实际跑过）。
