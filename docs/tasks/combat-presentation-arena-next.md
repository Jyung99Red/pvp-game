## 2. 相机共用，场地独立

相机算法已经在 `ui/ui_spatial_battle.js` 共用，但参数在 `pve/pve_profiles.js` 与 `pvp/spatial_duel.js` 重复，
视角转换又分散在 PVP 输入适配和共享绘制中。应集中维护相机与世界/屏幕转换，实例状态仍按本机每场独立创建。

- 共用：缩放、跟随平滑、少量移动预判、边界限制、屏幕与世界坐标转换、屏外判断。
- 相机只平移跟随与缩放，暂不做动态旋转，也不随朝向、移动或绕行旋转。
- 当前客机固定180°翻转是开局阵营坐标映射，不是跟随相机旋转；保留双方己方从下方开场的效果，整局映射固定。技能方向和文字保持屏幕方向。
- 独立：PVE/PVP 场地尺寸、出生点、墙块布局、主题；相机读取场地边界，不拥有场地规则。
- 本方案初始值：视野从396×440调整到374×416，人物显示约放大6%；宽高比例基本维持。后续微调再收紧到350×390。
  不通过改人物半径、攻击范围或世界单位实现拉近。未来应能独立覆盖视野参数。
- 保留少量预判，但采用稳定的显示帧时间；主机快照校正不能直接当成玩家高速移动来计算预判。
- 布局变化/Canvas恢复重新算视口；不重建对局、不改变角色坐标；相机状态不进存档和网络快照。
- 训练是否启用跟随相机不在本轮要求内，默认保留原模式。

## 3. 技能共享与 PVE 升级扩展

共用技能效果代码，用模式选择参数。

- 建立共享技能定义：ID、名称、方向、基础费用、基础效果参数。界面显示与执行读取同一份定义。
- 正式 PVE 参数入口可将基础定义与未来升级覆盖合成；本轮默认仍用现有数值，不实现升级经济、升级菜单或存档迁移。
- PVP 参数由固定的对战规则生成，不读取本地 PVE 技能升级；双方对同一规则版本必须得到一致参数。
- 公共执行流程负责可用性、排队和成功后扣点；各模式仍负责 SP 存放、获得事件、跨局继承与执行权限。
- 保留 PVP 客机预测的权限边界：升级配置或共享执行器不能让客机自行确定实际回血、伤害或胜负。
- 参数在开战时确定；有规则变更需更新协议/规则版本，避免旧技能参数客户端混战。

### PVP两个入口

模式名称按本方案定为“公平对决”和“养成对战”，默认突出公平对决。两者复用房间、模拟和界面，只切换战斗档案来源。

- **公平对决（fair）**：双方完全相同的固定战斗属性，不读取等级、装备、强化、幸运、属性加成或PVE技能升级。
- **养成对战（progression）**：保留当前装备/等级属性；四技能仍使用PVP基础参数，不带入未来PVE技能升级。
- 两模式都使用当前动作时序、四技能、满HP/AP与0SP开局规则；个人操作设置可以不同。
- 入口先选模式，再创建/加入房间。房间显示模式；模式不匹配则明确提示并禁止自动开战，不悄悄切换。
- hello/start/重赛携带并校验模式和规则版本。公平模式两端从本地同版本固定档案生成双方属性，拒绝不符档案；不能相信客户端上传的养成数值。
- 重赛保持模式；退出房间才能改模式。记忆房间码时一并保存模式，旧记录无模式视为养成对战。

公平档案第一版使用下面的设计初值（本方案提供，非既有数值）；Luna集中定义，勿自行引入平衡分支：

| 参数 | 固定值 |
|---|---|
| maxHp / atk / def / spd | 120 / 30 / 8 / 10 |
| apMax / critChance / guardThorns | 5 / 0 / 0 |
| earlyReleaseMs / parryWindowBaseMs | 300 / 180 |
| judgmentMultiplier / guardDamageMultiplier | 1 / 1 |
| motion各项倍率 | 全部1 |
| level档案字段 | 1，仅用于兼容；界面显示“统一属性” |

伤害、防御、AP恢复等继续走共享属性映射；不是另写固定伤害。公平模式不写回玩家养成存档。
公平指双方参数一致，不代表现有主机网络优势已经消失。

## 4. 优先修复：边移动边点放防御时对方视角卡顿

复现症状：移动中反复按下/松开防御，对方视角卡顿。根因待定位。

代码已有线索：

- `pveLogic.advance()` 每10ms子步经 `_processEvents()` 触发 `uiPve.updateFrame()`。
- `pvpLogic.advance()` 每子步刷新，外层 `loop()` 又刷新；输入消息与快照处理也会直接刷新。
- `uiPvp.updateFrame()` 每次计算墙钟dt并推进远端平滑；共享相机再按该dt计算位移速度。
  一帧内多次调用会产生很小且不均匀的dt，值得优先排查，但不是实机卡顿的确证。

重构目标：

1. 保持固定10ms模拟、命中和环境结算顺序、现有补帧上限；输入及时入队/执行，不等画面刷新才生效。
2. 逻辑事件在模拟层按原时点处理，例如 SP 增加、队列技能执行、奖励与胜负；不能为了批量绘制延迟这些逻辑。
3. 显示事件另行按顺序收集；每个显示帧只推进一次相机/远端平滑，只绘制一次Canvas和必要HUD。
4. 命中、格挡、技能事件不得因合帧丢失或重复；事件含发生时的位置/时间，不能统一用最终帧位置冒充命中位置。
5. 对局结束要显示最后状态与未消费事件；暂停、恢复、重赛清理事件队列，防止下一局播放上一局特效。
6. 远端平滑使用独立显示副本，不能写回权威或预测状态。防御朝向、举盾起点不能被插值重新启动。
7. 若仍卡顿，再排查消息频率、预测校正、重复输入、碰撞回退与主线程耗时；不要直接提高快照频率掩盖原因。
8. 不丢弃按下、松开、取消等离散输入；若合并拖动消息，必须保留离散事件顺序与网络序号语义。

优先复现场景：A持续按住移动，反复按下/松开防御，在B观察A；交换主客机重现。
同时区别是只有远端角色跳动、整个画面掉帧，还是本机相机抖动。

## 5. 武器与举盾表现

- 将“武器图标”按当前Canvas人物身旁的武器图形理解；沿用代码绘制，不默认增加图片资源或装备图标系统。
- 待机武器移到人物侧边，保持固定大小；出招围绕合理的持握点挥动，攻击预览仍来自引擎攻击快照。
- 盾牌平时在侧边，进入 `guard_start` 时平滑举到朝向前方，`guard` 保持前方，松开后回到侧边。
- 用已有动作阶段/计时驱动画面，远端晚收到状态时从正确进度显示，不每次快照都重播举盾。
- 这是表现调整，不改现有举盾生效时间、正面防御范围、弹反窗口、攻击范围、角色碰撞半径或移动倍率。
- PVP两名角色与PVE玩家共用人类绘制；PVE怪物不强加人类武器/盾牌。

## 7. 屏外敌人提示

“屏外”指相机画面之外，敌人仍在场地内；不会让角色走出场地边界。

- PVE/PVP共用：按实际相机窗口判断，在安全边缘画方向箭头；敌人回到画面隐藏。保留小幅滞回，避开HUD与控件。
- 阶段A没有内部遮挡，屏外箭头指向敌人实时位置；映射使用当前端的固定阵营视角，不旋转相机追敌。
- 阶段B加入墙后隐蔽后：无遮挡的屏外敌人仍有实时箭头；被墙挡住时只提示最后已知位置3秒，之后固定显示“对手位置未知”。
  未知状态不提供方向和距离。不得追踪隐藏敌人的真实位置；详细状态规则在墙体文档。
